# Windows: выполненные автоматические проверки и ручная приёмка

В текущей среде доступна Linux с Wine 10.0 и виртуальным экраном Xvfb. Это позволяет запустить собранный Windows EXE, проверить сообщения Win32, показать окно с игрой и сохранить снимок. Здесь нет настоящего рабочего стола Windows, физического GPU Windows, звукового выхода, двух контроллеров и webcam. Полная ручная приёмка Windows остаётся незавершённой. В отчётах она имеет `NOT_RUN`; автоматические проверки не меняют этот статус.

`GBStudio.exe --ui-self-test report.json demo.gbc` выполняет 20 проверок на видимых окнах: клавиатура, повтор клавиши паузы, виртуальная кнопка, передача захвата мыши, потеря/возврат фокуса, сброс Turbo/Rewind, блокировка фонового наклона и вибрации, выбор скорости/слота, полный экран и Escape. Окно и сообщения настоящие; сигналы XInput и состояния клавиш наклона подменены детерминированными функциями. JSON содержит `runtime: wine` или `windows` и `native_manual_validation: false`.

Прогон в Wine прошёл все 20 проверок. Отдельный `--self-test` успешно проверил CPU/GDI-отрисовку. Снимок [stage4-wine-gui.png](stage4-wine-gui.png) показывает обычный Windows EXE с загруженным CGB-демо в Wine, без подмены framebuffer. Он подтверждает появление изображения, но не качество Direct3D или быстродействие на Windows. Машинные результаты и хеши находятся в [stage4-windows-validation.json](stage4-windows-validation.json).

По результатам аудита исправлены четыре ошибки:

- Клавиши наклона больше не влияют на картридж, когда окно находится в фоне.
- При потере фокуса сбрасываются виртуальные кнопки и принадлежащий окну захват мыши.
- Обработчик `WM_CAPTURECHANGED` сохраняет захват, уже переданный другому окну.
- Вибрация выключена в фоне, даже если эмуляция продолжает выполняться, например при ограничениях паузы Hardcore.

Автоматический запуск всей Windows-проверки:

```powershell
powershell -ExecutionPolicy Bypass -File .\RUN_WINDOWS_QA.ps1 -OutputFolder .\qa
```

Скрипт открывает дополнительные окна для проверки фокуса. Во время прогона не переключайте приложения. Требуется интерактивный рабочий стол; изолированный сервис без desktop не подходит. Отчёт различает проверку GDI, сообщения Win32 и headless-запуски ROM.

Для ручной приёмки подготовлен отдельный исполняемый протокол из 18 пунктов. Сначала можно сформировать незаполненный отчёт:

```powershell
powershell -ExecutionPolicy Bypass -File .\RUN_WINDOWS_MANUAL_QA.ps1 -OutputFolder .\qa
```

Код завершения `2` означает незавершённую проверку. Скрипт не ставит `PASS` самостоятельно. Выполнение и запись наблюдений на настоящей Windows:

```powershell
powershell -ExecutionPolicy Bypass -File .\RUN_WINDOWS_MANUAL_QA.ps1 `
  -Interactive -ExecutionEnvironment NativeWindows -Tester "Имя тестировщика" `
  -ProgramFolder . -OutputFolder .\qa
```

В каждом пункте указаны действия и ожидаемый результат. После выполнения введите `PASS`, `FAIL`, `BLOCKED` или `NOT_RUN`, наблюдение и ссылки на доказательства. Указывайте модели устройств, драйверы, частоту звука, длительность игры, хеши ROM и точные ограничения. Не помещайте пароли и токены в отчёт. Протокол автоматически сохраняет хеши EXE/DLL и доступные сведения о видео- и звуковых устройствах; эти сведения сами по себе ничего не доказывают.

Пункты охватывают установку и Unicode/недоступную для записи папку, DPI и языки, клавиатуру и мышь, два геймпада, наклон и вибрацию, GDI/Direct3D и восстановление устройства, слышимый звук 44,1/48/96 кГц, смену аудиоустройства, час игры и синхронизацию, сохранения, webcam, Printer/IR, Link/обмен Pokémon, медиа/BESS, сервер RetroAchievements и пакет на чистых Windows 10/11. Неподдерживаемое физическое устройство отмечается `BLOCKED` с причиной; проверка эмулированного устройства не подтверждает физическое.

`PASS` всего ручного отчёта получается только после явного результата `PASS` во всех пунктах. `native_manual_validation` дополнительно требует выбранную среду `NativeWindows`. При работе в Wine указывайте `-ExecutionEnvironment Wine`; этот прогон остаётся отдельным свидетельством совместимости Wine.
